I Made a React App

aaronwatts@dev 8 June 2026

I made a React App. Well, I'm not quite done yet. There's some stuff I'd like to work out, such as useContext, and extracting my useEffect logic from the App component and into their own functions. But the app is working - I rebuilt an app I had already made using vanilla JavaScript. The two apps are functionally identical, but I thought it might be worth noting the differences somewhere.

The pros and cons of React have been heavily documented for years, so don't expect to read anything groundbreaking here. This is merely a reflection on some learning I've done lately.

I try to avoid unnecessary JavaScript where I can. I think HTML should be able to most things in a static site, JavaScript enhancements should ideally be modular and complimentary. In the situation where you don't have access to, or don't need a back-end server for something more functional, then I guess JavaScript is allowed.

A while ago I threw together a "web app" of sorts, that was intended as a complimentary tool for a project that piped scheduled TV shows that I follow to a Google Calendar. The web page existed only as a quick way to find show ID's without having to go through a bloated and over-informative front-end. It just showed me what I needed, nothing else. Oh, I did throw episodes by season in there as an excuse to play around with Simple CSS.

The app worked as intended. It wasn't fancy. It had terrible accessibility. But it did what I wanted it to. It connected to an API and updated the DOM accordingly. I made some design choices that were intended to reduce API calls out of respect to TV Maze, and keeping the calls to a minimum. I haven't gone back to fix the accessibility yet - as I've had it on the back of my mind that I would like to revisit the project, and skip the Google Apps Script phase and just print the schedule directly into an iCal file. I've been learning about iCal and I'm about ready to start that when my daily schedule allows.

I caught wind of something called web components in that time. They sound interesting. The kind of functionality you would get from a front-end framework, but natively in the browser. I've decided that might be something I might like to implement when I eventually go back to the project and inevitably get round to cleaning up the web page.

I've only ever really coded JavaScript in a JQuery without JQuery fashion. That is: I chop up and change the DOM based on events. At most I'll wrap the code in an App Class Object if the script is critical to the website. But nothing fancy like React. I looked at it years ago, I didn't really get on board. I wasn't making anything big, and the docs were a bit of mess during the transition from class based to function components.

I've learned a bit of it now. While I was reading about web components, it dawned on me that I don't really understand how a framework should work. It might be overkill, but I learned React, and will look at Lit components too, to work backwards to native web components.

I enjoyed the React development process. Though I still think it isn't really necessary for the size of projects I tend to work on - I can see why a large project with many devs would stand to benefit from the process. It is nice to work on things modularly, and in somewhat isolation from the rest of the code base - that's a concept I can get on board with, and I might actually be starting to look forward to using web components, even if I don't use them often.

What I didn't enjoy about using React is NodeJS is that it simply moves too fast. Trying to deploy my app on my Coolify instance was a headache. Using vite@latest just wouldn't work for me. I was getting BadEngine errors in my Docker container and then the deployment process would throw an error and exit. It deployed to Netlify with no issues at all, but I would expect this one as Netlify's main purposes for existing is to do exactly that. I eventually got a working Coolify deployment using vite@7, although even having to do that in the first place made me very aware that NodeJS will quickly change and vite version 7.x will no longer be supported and I'd likely have to go through the headache of updating everything. Curiously, I still got the same BadEngine errors, but the deployment completed this time, and everything is apparently okay now that I've set up health checks on the deployment (shrugs).

The old vanilla app is functionally identical to the new React app, with a static asset or two missing or different depending on when you look at it. The React app is running on a Pi at time of writing, so uptime and availability may vary. The expected differences apply: my ~5kB JavaScript file has been replaced with a ~200kB index-hash.js file, and the total size difference has jumped from ~45kB to ~237kB. If I'm being completely honest, I thought the React app size was going to be much bigger than that - maybe they've trimmed off some fat in the last few years? If that's the case, then well done to those responsible.

Memory usage is higher for the React app in firefox by almost double, from ~2MB compared to ~4MB, though React seems to manage memory over time better than the vanilla JS app. And memory usage for both apps seems to go between ~40MB and ~45MB for both apps in Chromium.

Performance differs a lot less than I had anticipated between React and JS. Although I still pride myself on keeping things small when they don't need to be big, so I won't be switching soon. But the process as a whole has made me keen to see how things stack up with the Lit library as well as native web components.
